Its RTCP scope covers fixed-point conversion, inverse/forward residuals, constraints, correction ramps, estimator handling, streaming pipeline, deadline detection, host guards, bridge backpressure, graceful stop and final cursor behavior. It explicitly does not validate real interrupt latency, motor/electrical behavior, or physical machine kinematics.
- The supplied MCU build profile targets STM32H723 / BTT Octopus Max EZ with `CONFIG_O5X_MCU=y`, `CONFIG_VM7_CLOSED_LOOP=y`, USB transport, a 128 KiB bootloader offset (`0x8020000` application address), and 25 MHz crystal.
- Native host tests passed locally: `o5x_host_v2_test.py` ran 47/47 tests and `o5x_host_guards_test.py` ran 2/2 tests successfully under Python 3.14 with bytecode writes disabled.
- No local GCC/Clang/MSVC toolchain or installed WSL distribution was available, so the C sanitizer/no-real suite could not be rerun on this Windows host. This is an environment limitation, not a test failure.
- The V2 stream input is not ordinary `G1 X Y Z A C`. It consumes `O5X_TCP` records containing true TCP `TX/TY/TZ` plus a unit tool-direction vector `I/J/K`, optional E/F and sequence/flags. MCU math derives U/V from IJK using `U=acos(K)` and `V=-atan2(J,I)`, then selects a continuous branch near the previous rotary cursor.
- Therefore a Grasshopper export that contains true TCP `XYZ + A/C` is conceptually compatible but not directly wire-compatible: it needs a deterministic A/C-to-IJK converter using the confirmed axis/sign/order convention, or the host protocol must be extended to accept explicit U/V.
- The branch contains no deploy-ready `[o5x_tcp]` printer configuration example. It provides parser defaults and a firmware `.config`, but machine-specific stepper names/inverts, step distances, limits, pivot/tool/work offsets, rotary zero/sign/order and real bridge enablement remain deployment inputs.
- No active or staged printer configuration outside the Git source contains `[o5x_tcp]`, RTCP geometry keys, bridge enablement, or `OPEN_FIVE_X_*` macros. Thus the source was preserved, but a machine-specific V2 deployment configuration was not.
- The staged deployment metadata explicitly excludes compiled firmware binaries from its archives. It references `klipper.bin` SHA-256 `de19dfe8...` and `klipper.dict` SHA-256 `574b8118...`, but the only located binary is the pre-R1 backup `klipper.bin` with the same `de19dfe8...` hash.
- All three deployment manifests state `firmware_flash_required: false` and target the ordinary four-Z wiring profile; they do not list the O5X host modules for deployment. This strongly suggests the staged R1 packages preserved the RTCP branch as Git history but did not activate the RTCP V2 runtime on `shu`.
- The custom branch history includes five main Open5X/RTCP commits from July 4–17, followed by a VM7 closed-loop commit. The final tree also includes many unrelated upstream/sensor/VM7 changes, so future recovery should isolate the RTCP commits rather than treat all 138 changed files as one deployment patch.
- No `klipper.dict` or other built firmware output was found anywhere under `/home/shu`, and the known pre-R1 `klipper.bin` contains no readable O5X/RTCP strings. Without the matching command dictionary, it cannot be proven that the referenced binary exposes the V2 MCU protocol; source must be rebuilt before deployment.

- The recovered GHX file explicitly exports `G1 ... X/Y/Z/A/C` with true TCP W-frame XYZ and controller-configured A/C angles. It declares `precompensated_machine_xyz: false` and `rtcp_required: true`, confirming it was designed for the tan-style XYZAC controller contract, not the shu V2 `O5X_TCP TX/TY/TZ/I/J/K` wire format.

- A full 8,540-motion-record historical GH true-TCP XYZAC file was converted mathematically to the V2 IJK representation and decoded back with the branch-selection rule. Under the current default mapping (`U=A`, `V=C`, zero offsets, positive signs), maximum recovered A/C error was below `6e-14 deg` and IJK norm error below `1.2e-16`. Thus the data itself is losslessly adaptable; the gap is protocol/coordinate binding, not missing path information.
- The same sample spans C from `-90 deg` to `-463.8 deg`; V2's nearest-period branch selection is necessary to preserve continuous multi-revolution C values.
- Static AST parsing succeeded for `o5x_tcp.py`, `o5x_tcp_stream.py`, `o5x_rtcp_preflight.py`, and the modified `klippy/stepper.py`.
- The real bridge requires five axis bindings, defaults to `stepper_x`, `stepper_y`, `stepper_z`, `manual_stepper u`, `manual_stepper v`, and requires U/V to be registered as extra axes before real motion. This is substantially different from tan's native XYZAC toolhead path.

Copying only `o5x_*.c/.h` and three Python extras would be incomplete.
